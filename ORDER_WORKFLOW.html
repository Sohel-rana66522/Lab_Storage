Order approval workflow

Client Portal order → Pending in the laboratory app → admin approves or rejects → stock and ledger update atomically → client sees the status.

Not compiled, not run, not tested. The environment this was written in has no Flutter/Dart SDK, and the Firebase Emulator could not be downloaded (storage.googleapis.com is blocked there). Nothing below has been executed. The Dart tests and emulator rules tests are written but unrun. Please run section 7 before relying on this.
Client submits (Pending)→Orders → Pending→ Admin reviews→Approve / Reject→Client: My Orders

1. One-time setup (required)

  1. Create at least one admin. In the Firebase console → Firestore, create a document users/<the admin's Auth UID> with the string field role = ADMIN (this is the existing UserRole.admin value). The UID is under Authentication → Users. Nobody can write users from the app; roles are granted only in the console. Without this, staff can see orders but Approve / Reject are hidden and refused.
  2. Deploy the new rules (they are required: the old rules do not allow approval).
  3. Recommended: in Authentication → Settings → User actions, turn off "Enable create (sign-up)". See section 5, caveat 1.
firebase deploy --only firestore:rules
# no Cloud Functions and no new indexes are needed

2. How approval works

OrderAdminRepository.approve() runs ONE Firestore transaction:

  1. Reads the order. Not found → error. Already Approved → stops and writes nothing. Rejected → error.
  2. Reads users/{uid} and requires role == ADMIN.
  3. Reads every requested chemical by its real document id (the order only keeps a name/formula snapshot).
  4. Validates all items with TransactionRepository.planEntry(): chemical exists, unit compatible, quantity > 0, enough stock (the same code manual entries use, units converted, never negative). If any item fails, an error listing every problem is thrown before any write.
  5. Writes, together: for each item the chemical's new currentStock (new = current − issued) plus one ledger entry of the existing usage type OUT (via TransactionRepository.stageEntry(), the same writer manual entries use), then the order: status=Approved, approvedAt (server time), approvedBy (uid), approvedByName, transactionIds.

Each ledger entry carries orderId, the client's name and ID (as studentName/studentId), purpose Client order LAB-XXXXXXXX and the supervisor in remarks, so it appears in Recents, chemical history and reports like any other usage. Success is reported to the admin only after the transaction commits.

Preventing duplicate deductions

  • The status check and all writes are in one transaction; a concurrent approval is retried by Firestore, sees Approved and writes nothing.
  • Ledger ids are deterministic (LAB-XXXXXXXX-1, -2, …). A repeat can only target the same documents, and ledger entries cannot be updated (rules), so it cannot be written twice.
  • The rules allow an order-linked ledger entry only in the same request that moves that order from Pending to Approved, so no later request can add another.
  • The Approve button is disabled while a request runs, and a second approval of an approved order returns "already approved" without writing.
  • If the connection drops mid-commit, the app reads the order from the server before saying anything: approved → reports success; still Pending → "nothing was deducted, try again"; unreadable → "reload and check before retrying".

4. Firestore data

orders/{LAB-XXXXXXXX} keeps the existing fields (clientName, clientId, supervisorName, items[], itemCount, status, clientUid, createdAt; each item keeps the name/formula/quantity/unit snapshot plus chemicalId) and gains, only when relevant: approvedAt, approvedBy, approvedByName, transactionIds, rejectedAt, rejectedBy, rejectedByName, rejectionReason, updatedAt. transactions/{orderId}-{n} gains orderId. users/{uid} (role) is read-only from the app. The existing naming (handledBy, staffNote in the old rules) was never written by any code and has been replaced.

5. Security

  • Clients (anonymous sessions) can create a Pending order and read only their own orders. They cannot approve, reject, edit or delete any order, change stock, or touch the ledger.
  • Approve/Reject require users/{uid}.role == 'ADMIN', enforced in the rules, not just by hiding buttons. approvedBy/rejectedBy must equal the caller's uid; times must be server time; only the listed fields may change; Approved and Rejected are final.
  • Order-linked ledger entries need an admin, type OUT, id <orderId>-n and the order moving Pending → Approved in the same request.
  • No Cloud Function was added. The project is on the free plan and already relies on rules plus Firestore transactions; all privileged writes are done by signed-in staff whom the rules check. A Cloud Function would remove the item cap below but needs the Blaze plan.
Caveats you should know about
  1. Any non-anonymous account is still “staff” for everything except order approval (existing behaviour, unchanged so your manual workflow keeps working). If Email/Password sign-up is enabled in Firebase Authentication, anyone with your public web API key can create an account via the REST API and then edit stock and the ledger. Disable sign-up (setup step 3) and create accounts only in the console. Moving all staff access onto the admin role is a small further change if you want it.
  2. 7 chemicals per order. Firestore allows 20 document lookups per commit in rules; an approval needs about 2 per item plus 3. This count was derived from the documentation, not verified on the emulator. The client cart, the approval code and the rules all enforce 7; keep them in step if you change it.
  3. Rules can only spot-check the first and last ledger entry of an order (they cannot loop). The approval code writes all of them in the same transaction.
  4. My Orders is tied to the anonymous session: another browser or cleared site data will not show earlier orders.
  5. The Orders tab was added as a sixth bottom-navigation item on phones, which is tight on narrow screens.

6. Error handling

SituationWhat the admin sees
Insufficient stock / missing chemical / bad unit or quantityA red message listing every failing item; nothing written, order stays Pending. The detail screen also warns before you press Approve.
Already approved / rejected"Already approved — no stock was changed" / a clear refusal.
Order not foundMessage, and an empty-state page.
Not an adminButtons hidden with an explanation; the transaction and rules also refuse.
Concurrent approvalThe second attempt sees Approved (or is told the outcome); stock moves once.
Network / Firestore failureOutcome is verified from the server before any message; no success message unless confirmed. Diagnostics go to dart:developer logs (OrderAdminRepository).

7. Testing

Written, not run

  • test/order_approval_logic_test.dart — stock maths (deduct, exact depletion, never negative, unit conversion), order shape checks (duplicates, bad quantities, item cap), deterministic ledger ids. Run: flutter test.
  • test_rules/orders.rules.test.js — rules against the Firestore Emulator: client submit/read-own/no-approve, admin approval commits everything, missing ledger refused, spoofed approver refused, non-admin refused, second and racing approvals refused, rejection leaves stock alone, final states, manual stock entry still works. Run: cd test_rules && npm install && npm test (needs Java 11+).

Not covered by any automated test

The Dart transaction itself (multi-item atomicity, insufficient stock across items, retry after a network failure) needs the Firebase emulator with the Flutter SDK; no Dart-side emulator test exists. Check these manually:

  1. Submit an order as a client → it appears under Orders → Pending without a refresh.
  2. Approve a 3-chemical order → three OUT entries appear in Recents with the order id; each chemical's stock dropped by the requested amount; the client's My Orders shows Approved.
  3. Make one chemical short (record a usage first), then approve → error naming it; no chemical changed; order still Pending.
  4. Double-click Approve; open the same order on two devices and approve on both → stock drops once.
  5. Turn off Wi-Fi mid-approval → no success message; reload the order and confirm its true state.
  6. Reject with and without a reason → no stock change; the client sees Rejected and the reason.
  7. Sign in as a staff account with no users document → Approve/Reject hidden.
  8. Record manual Add Stock and Record Usage → still work and chain balances correctly.
