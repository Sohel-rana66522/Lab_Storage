Lab Ledger — Client Portal

A separate, read-only front door to the same Firestore data as the laboratory app. Clients browse folders, see the real available quantity, build a cart and submit a chemical request.

Home (folders)→Folder (chemicals)→Cart→ Order request→Order submitted
Before you run it: the portal has not been compiled or run yet. The environment it was written in has no Flutter SDK. Run flutter pub get, flutter analyze and flutter test first (steps below), and use the test checklist at the end.

1. One-time setup

  1. Enable anonymous sign-in. Firebase Console → Authentication → Sign-in method → Anonymous → Enable. Without this the portal shows "not switched on yet" and cannot load any data.
  2. Publish the new security rules. Paste firestore.rules into Firestore → Rules → Publish (or firebase deploy --only firestore:rules). Do this before the portal goes live.
  3. Install the new package (shared_preferences, used to keep the cart across a page refresh): 
    flutter pub get
  4. Check it: 
    flutter analyze
flutter test
  5. Run the portal (the laboratory app still runs with plain flutter run): 
    flutter run -d chrome -t lib/main_client.dart

2. Hosting the portal

The laboratory app and the portal are two builds of the same project, so give each its own Firebase Hosting site. Keeping them on separate addresses also keeps staff logins and client sessions apart (browser sign-in is stored per address).

flutter build web -t lib/main_client.dart --release
Copy-Item -Recurse build\web build\client      # PowerShell; use cp -r on macOS/Linux

firebase hosting:sites:create your-client-site-name
firebase target:apply hosting client your-client-site-name

Then add this to firebase.json and deploy with firebase deploy --only hosting:client:

"hosting": [
  { "target": "client", "public": "build/client", "ignore": ["firebase.json", "**/.*"] }
]

Build the laboratory app into its own folder the same way (flutter build web, then a separate hosting target).

4. Order data

Collection orders, document id = order ID (for example LAB-7K3MQ9XP).

FieldValue
idSame as the document id.
clientName, clientId, supervisorNameAs typed by the client.
status"Pending" on creation (the project had no earlier status convention).
createdAtServer timestamp.
clientUidFirebase uid of the anonymous session that sent it.
itemCountNumber of chemicals in the order.
items[]chemicalId, chemicalName, formula, requestedQuantity, unit, categoryId, categoryName, plus baseQuantity and baseUnit (the same amount in the unit the lab tracks the chemical in) and availableAtRequest (stock seen when ordering).

Example: a client asks for 500 mL of a chemical the lab tracks in litres. The item stores requestedQuantity: 500, unit: "mL" and baseQuantity: 0.5, baseUnit: "L", so staff can compare it directly with the ledger.

Stock is never changed by the portal. Submitting only creates a Pending request. Actual issuing and stock deduction still happen through the existing Record Usage workflow in the laboratory app.

5. Security

How clients are identified

Clients sign in anonymously and automatically; there is no client login screen. The existing rules treated every signed-in user as full-access staff, which would have given every anonymous visitor write access to your inventory. The rules now define isStaff() as "signed in and not anonymous". Your laboratory accounts (email + password) are unaffected.

CollectionClient portal (anonymous)Laboratory staff
categoriesReadRead, create, update, delete
chemicalsRead (live currentStock)As before (stock only changes through a paired ledger entry)
transactionsNo access (it contains student names)As before
ordersCreate only, with strict shape checksRead; update processing fields only (status, updatedAt, handledBy, handledByName, staffNote); no delete

An order is accepted only if: it has exactly the expected fields; the ID matches LAB-XXXXXXXX and the document id; clientUid equals the sender's uid; status is Pending; createdAt is the server time; the three text fields are non-blank and within length limits; and it has 1–50 items. An existing order can never be overwritten, so one client cannot alter another's request.

Things to know

  • Stock is checked in the app, not in the rules. Rules cannot loop over an order's items, so "quantity ≤ available" is enforced by the app, which re-reads stock from the server at the moment of submission. A modified client could bypass that, which is harmless here: the order is only a request and staff still approve what is issued.
  • Clients can read whole chemical documents (location, notes, CAS, minimum stock), not just the available quantity. Firestore cannot hide individual fields. If that matters, a later step is a separate public "catalogue" collection kept in sync by staff or a Cloud Function.
  • Anonymous access can be scripted. Anyone can obtain an anonymous session. Turning on Firebase App Check for the portal is recommended to limit abuse.
  • Staff accounts are trusted fully (unchanged). Keep creating them manually in the Firebase console; do not enable email sign-up.

6. How the portal behaves

  • Home: the laboratory's folder grid (FolderCard) with search by chemical name or formula (H2SO4 also finds H₂SO₄). The staff-only low-stock count is hidden.
  • Folder: each chemical shows name, formula, available quantity with unit, a stock chip and Add / Remove. Depleted chemicals cannot be added.
  • Cart: − / + buttons, a typed quantity, and a unit switch between compatible units (L ↔ mL, kg ↔ g ↔ mg) that converts the amount. Quantities above the current stock are flagged and block the next step. The cart is kept in this browser, so a refresh keeps it; availability is always re-read live.
  • Order: name, ID and supervisor are required. On submit, the current stock is re-read from the server; if anything no longer fits, nothing is saved and the problem is listed. On success the cart is cleared and the order ID is shown. The page never says chemicals were issued.
  • Layout: phone = top bar + floating cart button; tablet = navigation rail; desktop = extended sidebar (same breakpoints as the laboratory app). The cart icon shows the number of chemicals.

7. Not built (outside this request)

  • No screen for staff to see orders yet. Until one is added to the laboratory app, review orders in the Firebase console under orders. OrderModel.fromFirestore is ready for a future Orders screen.
  • Clients cannot look up an order after submitting it (they keep the order ID shown on screen).
  • The order ID is the only reference; there are no emails or notifications.

8. Test checklist

  1. Open the portal: folders appear with the right chemical counts.
  2. Open a folder: chemicals show the same available quantity as in the laboratory app.
  3. Record a usage in the laboratory app: the portal's quantity updates live, without a refresh.
  4. Add two chemicals; the cart badge shows 2. Refresh the page: the cart is still there.
  5. Change a unit (L → mL): the quantity converts. Type a quantity above the stock: it turns red and "Proceed to Order" is disabled.
  6. Type 0 or clear the box: blocked. Remove an item: the badge drops.
  7. On the order page, submit with each field empty in turn: each shows an error and nothing is saved.
  8. Submit a valid order: the success page shows LAB-XXXXXXXX; a document appears in orders with status Pending; chemical stock is unchanged.
  9. Turn off the network and submit: a clear "no internet" message, and the cart is kept.
  10. Rules check (Rules Playground or a script): an anonymous user cannot update a chemical, create a folder, create a transaction, read orders or edit an order, and a staff account still can do all its usual work.
  11. Resize the browser from phone to desktop width and check each page.
